# 容错与异步消息

## 下游慢或不可用

1. 为整条请求设截止时间，向每一跳分配剩余时间。核对连接池等待、建立连接、首个响应和整个操作都能在预算内退出。
2. 只对明确可重试的错误和具备幂等语义的操作重试。按业务确定重试上限、退避和抖动。检查代理、客户端 SDK、编排器和 Worker 是否重复重试，把尝试次数和用时算在同一预算里。结果未知的写请求先按操作标识查询或对账。[HTTP 幂等语义](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods)
3. 用并发上限、独立连接池或 Worker 池隔离慢依赖。持续故障时考虑熔断并定义恢复探测。降级可以省略图书推荐，对借阅资格或资源授权等关键判断则返回可识别的失败状态。

**验收证据**包括向依赖注入延迟或错误，记录实际尝试次数，确认请求按预算结束，以及其他路由和后台任务仍能使用各自资源。依赖恢复后验证有限探测及逐步恢复。

## 可靠异步与消息积压

- 明确主流程完成条件和后续副作用。借阅写入成功后，通知、统计和推荐可以独立消费事件。确实需要在返回前完成的业务动作使用该操作的同步确认或可查询状态。
- 任务或者事件必须与业务写入一起可靠存在时，将数据库变更和 outbox 记录放在同一事务。转发器有重试和积压告警；发布后、标记前掉线会导致重复投递，消费者需要按至少一次语义处理。
- 需要可靠性时用可持久恢复的队列或任务存储。按消费者上限排队，监控积压量、最老消息年龄、成功处理速率和死信。流入持续超过处理能力时安排削流、扩容或暂停低优先级工作。
- 用稳定事件 ID 协调去重和业务写入。数据库内副作用与消费记录能放在同一事务时，一起提交后确认。外部副作用使用提供方幂等键、回执查询或对账路径。把重复投递、延迟、乱序和恢复当成可验证场景。
- 顺序要求落实到业务键和版本，例如按一个会话处理事件或只接受更新版本。死信重放采用同一幂等身份和权限检查，说明哪些消息适合回放。

**验收证据**包括数据库提交后发布失败仍能补发，重复消息只产生约定的业务效果，Worker 在提交和确认间结束时可以恢复，以及队列拥堵时在线请求仍满足约定。
