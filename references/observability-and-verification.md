# 可观测性与故障定位

## 定位一次真实故障

- **指标发现问题。** 先看实际吞吐、错误率和尾延迟，再下钻应用资源、依赖连接等待、队列年龄或模型首段延迟。核心业务成功率与 HTTP 成功率分别记录，例如返回 `202` 的比例和报告真正完成的比例。
- **追踪定位故障位置。** 从入口到 API、数据库、模型、工具和队列传播追踪上下文。异步消费与发起操作可关联到同一业务身份。保留关系足以区分等待、重试和真正执行的耗时。
- **日志确认当时行为。** 结构化记录操作、结果、失败分类和稳定标识。使用 trace、任务或操作 ID 关联。限制敏感内容和高基数指标标签，按项目需要采样请求正文和模型数据。
- **告警明确触发条件。** 绑定用户影响、观测窗口和排查入口。基于已有基线和业务目标选阈值。版本、流量和指标查询范围一起核对，便于比较灰度与基线。

## 核对观测本身

- 沿实际入口发出一条可识别的请求，确认错误归因、版本、结果和耗时在每层都能对应到同一次操作。确认失败、重试、取消等分支也会记录各自事件。
- 使用能复现目标故障的检查验证告警。按实际流量和时段判断指标口径，明确无数据、采样及迟到事件的处理。对任务和模型调用分别记录业务效果和调用结果，避免把一次任务多次尝试的指标混作业务成功数。

选择功能、失败和恢复验收场景时见[后端验证矩阵](verification-matrix.md)。
