# 服务入口与流量治理

先画一条真实路由，例如 `客户端 → 入口代理 → API 网关 → 业务服务实例`。标明每跳是否终止 TLS、修改路径、校验身份、重试或缓冲。单个入口组件可以兼任代理、负载均衡和网关职责。

| 职责 | 选择条件和边界 |
|---|---|
| 反向代理 | 对外提供统一域名和 TLS，按配置将请求转发到上游。需要同时检查 DNS、证书、路径改写、请求体大小和连接超时。 |
| 负载均衡 | 为同一逻辑服务的可用实例选择目标。选用与请求耗时和长连接相符的分流方式，并在实际负载下验证。 |
| API 网关 | 多入口、多服务路由或者统一鉴权与配额带来收益时引入相应能力。例如将 `/api/tasks` 与 `/api/files` 路由到各自的上游，按需要转换协议。资源访问权和业务写入条件由相应业务服务判定。 |

## 入口契约

- 在受控的代理边界生成或覆盖转发头和身份上下文。只信任已知上游设置的 `Forwarded`、`X-Forwarded-*` 或身份头。用户、租户和资源权限在执行点重新核对，内部直连路径也要符合权限约束。
- 指定外部路径、上游路径、协议及请求 ID。已有网关映射多次改写路径时，用实际登录用户发一条请求，对照网关日志与上游日志。
- 把启动、存活和可接流量区分开。就绪失败时停止分配新请求，替换前处理已有连接和任务。只有进程卡死且重启有助恢复的条件适合作为存活探测。
- 明确限流键、作用域、超过预算的响应和恢复方式。按用户、租户或路由隔离额度时确认计数范围。多实例需要共享或协调决策时，按部署拓扑验证全局上限。
- 入口放大规模后也要核对网关自身的连接数和可用性。`502` 优先查上游连接或响应，`504` 比较各层超时和下游等待。以请求 ID、上游状态和时间数据归因。

## 流式响应经过代理

- 用生产同类代理确认 SSE 的首个事件和后续增量能及时抵达。分别核对响应缓冲、压缩、心跳、闲置超时和并发连接限制。
- 测试中途关闭连接后的订阅清理。代理是否关闭连接和后台任务是否继续，由任务契约分别决定。需要重连补播时见[任务与流式响应](tasks-and-streaming.md)。
- 有多实例或滚动更新时，至少验证一个实例摘除、一个连接重连和一条跨实例任务查询。用路由、授权、事件顺序和最终结果作为验收证据。
